## Notes

- **CI build failure and fix (2026-10-16).** The first build of this image, CI run 38669069783, failed at the apt step with `E: Version '2.0.7-1' for 'sslscan' was not found`. Both intended versions were confirmed present in bookworm via `sources.debian.org/api/src/<pkg>/` (`sslscan` 2.0.7-1 in bullseye,bookworm; `testssl.sh` 3.0.8+dfsg-1 in bookworm), so the pin is not reproducible against this base image's apt sources. The exact apt pins were removed and `dpkg-query -W` now prints the resolved versions into every build log, so what the image contains is recorded even though it is not pinned.
- **The image installs five local tools; the sixth sub-source is an API call.** testssl and sslscan come from the base image's Debian suite (unpinned, resolved versions echoed at build time; see the CI note above); certgraph and tlsx are installed with the project's own Go module path pinned to the release tag, mirroring `docker/subfinder/Dockerfile` (`FROM golang:1.26-bookworm` + `RUN go install <module>@vX.Y.Z`); cipherscan is `git clone`d and checked out at the pinned commit above, and its tolerance-scan dependencies (tlslite-ng, python-ecdsa) are pre-provisioned at the pinned releases above in exactly the layout `cscan.sh` expects (a `tlslite` and an `ecdsa` directory importable from the repository root), so no scan ever clones anything at run time. The runner invokes each tool with an argv list through `subprocess.run`; no shell string is ever built.
- **Auth: none except the free SSL Labs registration.** No sub-source needs a paid key. The SSL Labs v4 `analyze` call documents a mandatory `email` header holding the address registered through the free `register` call; the runner reads it from `SSLLABS_EMAIL`, sends it only when it is set, never prints it and never records it in the command it reports. When the variable is unset the sub-source is reported as a documented skip instead of sending a request the documentation says will be rejected with 441.
- **One assessment per sub-source per run.** The runner makes at most one API call and one local invocation per sub-source; it does not paginate, does not poll SSL Labs repeatedly and does not run sub-sources in parallel. CipherScan's single invocation internally drives its bundled OpenSSL client many times against the one target it was given - that is the tool's own documented operation - and the runner adds no calls of its own.
- **No invented severity.** testssl.sh documents the severities OK/INFO/WARN/LOW/MEDIUM/HIGH/CRITICAL in its JSON output and SSL Labs documents endpoint grades (A+, A-, A-F, T, M); those are normalized. sslscan, certgraph, tlsx and cipherscan publish no severity classification, so their records are recorded with severity "info" rather than an invented rating.
- **What the runner parses.** testssl.sh: the documented pretty JSON file (`--jsonfile-pretty`), reading the documented identifier/severity/finding values (the reader accepts the flat `--jsonfile` array or the structured `--jsonfile-pretty` sections and the `id`/`identifier` spelling). sslscan: the XML written by the documented `--xml=<file>` option, reading only the elements the project's own `sslscan.c` emits with `printf_xml` — `<cipher status="..." sslversion="..." bits="..." cipher="..." id="..." strength="..."/>`, `<heartbleed sslversion="..." vulnerable="0|1"/>`, `<renegotiation supported="..." secure="..."/>`, `<compression supported="..."/>` and `<fallback supported="0|1"/>`; sslscan's XML emits no protocol element, so no protocol record is claimed. certgraph: the `-json` graph map (nodes/links/depth/numDomains plus certgraph metadata), whose node shape is defined by the project's own `graph.DomainNode.ToMap` / `graph.CertNode.ToMap`. tlsx: the documented JSONL output of `-json`, reading the documented field names from the README's JSON example. cipherscan: the JSON object its own `display_results_in_json` emits (README: "Exporting to JSON with the `-j` command line option"), reading `target`, `utctimestamp`, `serverside`, `renegotiation`, `compression`, the `configs` object and the `ciphersuite` array's `cipher`/`protocols`/`pubkey`/`sigalg`/`trusted`/`ticket_hint`/`ocsp_stapling`/`npn`/`pfs`/`curves`/`curves_ordering` values verbatim (the script writes every one of them as an OpenSSL-style string such as "True"/"False" and this runner never converts them). Anything a tool does not publish is left absent rather than guessed.
- **--health never touches the network.** `docker run --rm --network none <image> --health` prints exactly `ok` on stdout and an inventory JSON line on stderr listing each sub-source, whether its binary is present and whether the optional SSL Labs credential is configured. It starts no subprocess and opens no socket.
- **--selftest-cipherscan scans only loopback.** The capture case runs `docker run --rm --network none <image> --selftest-cipherscan`: a self-signed certificate is generated with the system openssl, a local `openssl s_server` answers on 127.0.0.1, the pinned CipherScan checkout scans it through the very same code path as a real run, and the server is stopped again. It exercises the checkout end to end - including the pre-provisioned tolerance-test dependencies - without touching any host outside the container; no other network access is used.
- **Direct probes require authorisation.** testssl, certgraph, sslscan, tlsx and cipherscan all connect to the target host itself (CipherScan through its bundled `openssl s_client`); the adapter therefore declares `requires_authorization_assertion=True`.
